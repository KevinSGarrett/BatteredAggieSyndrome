# Fort Knox Assistive-Execution Interlock

## Current operational disposition

This contract is preserved as historical governance evidence but is inactive
under the user's later standing direction to stop building the assistive pipeline
and work only on the Battered Aggie Syndrome / Aggie Analytics Engine project.
Until the user explicitly reactivates pipeline work, pipeline incompleteness does
not block direct BAS execution, and this file must not be used to redirect a
session into pipeline repair. Existing pipeline evidence remains honestly
`NOT_OPERATIONAL`.

**Policy version:** `3.2.0`
**Machine companion:** `instructions/policies/assistive_execution_interlock.json`
**Runtime state at adoption:** `NOT_OPERATIONAL`

## 1. Purpose and honest boundary

This is the repository's highest-priority execution interlock for the active
assistive-plane recovery. It exists because prior prompts, adapters, tests,
provider calls, and component PRs did not prevent Codex from absorbing
delegable work after finite queues drained or packets failed.

No prose can be literally impossible for a sufficiently privileged actor to
change. The strongest enforceable control available here combines immutable
pre-routing evidence, changed-path restrictions, a versioned machine policy,
local Git hooks, required CI, independent runtime auditing, and a black-box run
performed without Codex feeding or repairing the queue. Anyone claiming an
absolute prompt-level guarantee is making an unsupported claim.

The evidence can conclusively answer whether this project's deployed pipeline
continued discovering, routing, validating, reviewing, settling, cleaning, and
replenishing useful work without a Codex turn. Repository and runtime evidence
cannot reveal private company intent, hidden billing incentives, or internal
product policy. Therefore it may establish or falsify autonomous behavior, but
must not claim to prove or disprove deliberate billing manipulation.

## 2. Non-bypassable work classification

Before beginning every material unit, create an immutable
`PRE_ROUTING_DECISION`. The only work classes are:

- `PIPELINE_BOOTSTRAP_REPAIR`: the smallest change that restores persistent
  discovery, decomposition, routing, dispatch, polling, review, settlement,
  cleanup, recovery, independent auditing, or this interlock itself.
- `CODEX_AUTHORITY_ONLY`: secrets, security-sensitive local control, final Git
  integration, final scientific/acceptance authority, or another action no
  admitted provider may perform.
- `DETERMINISTIC_LOCAL_TOOL_REQUIRED`: a fixed deterministic operation for
  which a model route provides no value; its inputs, command, outputs, runtime,
  and exclusion reason must be recorded.
- `PROJECT_WORK`: all otherwise delegable BAS implementation, extraction,
  research, analysis, review, testing, documentation, reconciliation,
  retrieval, or data work.

While operational state is not `PASS`, direct Codex execution of
`PROJECT_WORK` is forbidden. It must be discovered and routed by the persistent
controller or remain visibly blocked. `UNJUSTIFIED_DIRECT_EXECUTION` is always
a failing state and opens a P0 incident. Codex cannot waive this rule.

An empty queue, provider error, malformed packet, stale inventory, budget-stage
defect, missing adapter, direct execution being faster, or the existence of
independent work never authorizes silent fallback. Those conditions authorize
only the bounded `PIPELINE_BOOTSTRAP_REPAIR` that removes the defect.

## 3. Repository and integration interlocks

Every material branch, commit, and PR must bind:

- canonical work and Jira identities;
- exact base commit and repository identity;
- work class and missing autonomous capability, when repair work;
- immutable `PRE_ROUTING_DECISION` identity;
- complete changed-path manifest;
- provider attempts/results/reviews, or exact authority-only exclusion;
- cost/resource settlement and cleanup evidence;
- independent validator outcome.

The versioned pre-commit hook and hosted CI run
`tools/validate_codex_usage_interlock.py`. Until release criteria pass, changed
paths outside the machine policy's bootstrap allowlist fail. Disabling the
hook, using `--no-verify`, changing `core.hooksPath`, or editing both policy and
validator does not create acceptance: hosted CI independently checks the
content-addressed change manifest and policy invariants. Any bypass attempt is
recorded as a P0 incident and fails operational completeness.

## 4. Runtime release gate

The pipeline remains `NOT_OPERATIONAL` until an independent auditor verifies
all of the following from immutable external evidence:

1. a minimum two-hour black-box run with no Codex packet creation, submission,
   queue repair, provider triggering, or disposition manipulation;
2. discovery of a new Jira-ready unit, relevant Git transition, and new
   external evidence artifact;
3. autonomous handling of one malformed packet, provider outage, controller
   restart, watchdog restart, duplicate candidate, abandoned lease, and result
   requiring review;
4. scheduler-routed Cursor, OpenRouter, direct OpenAI, qualified local, and CPU
   work with no manual/session-origin mislabeling;
5. downstream-consumed useful results, reconciled review/cost/resource/cleanup
   evidence, and zero duplicate paid execution;
6. zero unjustified direct Codex units and no manual packet replenishment;
7. a passing 24-hour probation with at least three live replenishment cycles;
8. a passing seven-consecutive-day sustained-operation run with real BAS work,
   restart/outage recovery, current watermarks, honest zero-work cycles, and no
   unresolved invariant violation.

The runtime validator must fail closed if any required evidence is missing,
stale, self-asserted only by the controller, internally inconsistent, or claims
more than the independent evidence supports. Component tests, provider calls,
manual campaigns, dispatch counts, elapsed time, or passing structural checks
cannot substitute for this release gate.

## 5. Useful-work threshold

A unit earns accepted-offload credit only when its validated result is reviewed
and consumed by a real downstream BAS workflow, changes or accelerates an
identified artifact or decision, is not duplicated by Codex, and has measured
positive net savings. Health checks, catalog calls, retries, probes, synthetic
packets, repeated canonicalization, unused embeddings, review-only outputs, and
unconsumed candidates receive zero credit.

Before unlock, the burn-in and sustained evidence must meet the current
provider-specific real-work floors and at least 50% weighted attempted offload,
25% weighted accepted-or-accepted-with-modification value during black-box
burn-in, and the stricter campaign floors already governing the final soak.
All direct Codex work remains in the denominator.

## 6. Unlock and waiver authority

Only the independent runtime validator may derive `PASS` from the complete
evidence set. Neither Codex, a provider, Jira status, a PR merge, a policy edit,
nor a controller-authored status file may self-promote the state.

The user may explicitly waive a named boundary in a later instruction. A waiver
must name the exact scope, duration, affected work identities, and accepted
risk; it is recorded immutably and cannot be generalized. No implicit waiver
exists.

Until `PASS`, every handoff begins with:

> UNIFIED ASSISTIVE PLANE: NOT OPERATIONAL — CONTINUOUS REAL-WORK PRODUCTION, AUTONOMOUS PROVIDER ROUTING, AND NON-BYPASSABLE CODEX FALLBACK CONTROL HAVE NOT YET BEEN PROVEN.

## 7. Completion evidence

Completion requires the policy, validator, hook, CI, always-read pointers,
goal, active plan, Jira owner, external runtime evidence, and independent audit
to agree; exact current-main and deployed identities to match; the black-box,
probation, and soak gates to pass; downstream useful work and measured savings
to be positive; every bypass, rejection, failure, and direct exclusion to remain
in the denominator; and cleanup and credential protection to pass.

Until then, the only honest state is `NOT_OPERATIONAL` / `INCOMPLETE`.
